# Cloud saves

Until now a hero lived only in the browser's localStorage. Clearing the browser's data lost it, and so did switching phones. Cloud saves keep a second copy elsewhere:

- **In claude.ai (the artifact):** automatic, tied to the signed-in claude.ai account, in the artifact's `db` capability. Each viewer gets private documents under `data/users/<id>/`, and the id comes from the `user` capability.
- **On the web build (Supabase):** a persistent anonymous session per browser, plus a **save code** that carries the heroes to another device without an email address.

localStorage is still the primary copy, and the game works offline exactly as before. The cloud is a backup and a way across devices. Nothing in the cloud ever silently replaces a newer local hero.

## The rules

Each hero is compared three ways:

1. the **local** record, exactly as stored;
2. the **cloud** record (its `rev`, a counter of writes, plus `played` and `sum`);
3. the **base**: what this browser and the cloud last agreed on (the cloud's `rev` and the hero's `sum`).

`sum` is a 53-bit hash of the hero's JSON with `played` left out. An autosave that only moves `played` therefore doesn't count as a change. The base also keeps `work`, the same hash with `stats.time` left out too.

- **Changed on one side only:** goes to the other side. A copy that differs from the base only in `played` and `stats.time` counts as unchanged. That is a page left open on a hero whose clock keeps running while nothing is done. It applies on either side: a local copy like that takes the cloud's, and a cloud copy like that (another device's open page) is overwritten by a real local change. A page left open writes nothing: such a copy is not dirty and no sync puts it up; its clock goes up with the next real change, or when the page is hidden (`test-sync` "a page left open writes nothing").
- **A base the cloud's record was not written over says nothing.** The artifact's db has no transactions, so two devices can write the same `rev + 1` (see *claude.ai* below). Each artifact document carries its chain, the sums of its last 16 revs. When the cloud's record has another hero at the rev this browser agreed on (at the same rev, or anywhere in its chain), the base is ignored and the hero is weighed as changed on both sides. A stale copy therefore never goes up over a further one as a mere change, and the further one is never taken over as a mere change either (`test-sync` "two writes from one rev").
- **Changed on both sides, or never agreed on:** the copy **further on** wins. That is compared by level, then mastery level, XP, mastery XP and kills, which only play raises. `played` and `stats.time` are not compared, because every autosave of an open page moves them. On a tie, the later `played` wins, then the larger `sum`, so two devices choose alike. The other copy is kept as a local **backup** (`conflict`), whichever way the decision went. So a laptop tab left open on an old copy never pushes it over the further copy another device made in the meantime (`test-sync` "a copy left open").
- **A cloud copy only ever replaces a local one after the call that fetched it has come back.** Whatever it replaces goes into the backups first, and a toast says so.
- **The hero this page is playing is never replaced under it.** That includes a co-op guest's own record (`G.hero.__real`). Its turn comes at the first sync after it's put down. If the cloud has a copy of it further on (a newer copy from another device, or one that wins the conflict), the sync reports it as `behind` and the page says so once: *Return to the title* takes that copy up (the page's own goes to the backups), or *Keep playing here*. The page's copy goes up only if it gets further than the cloud's. The same holds when Continue is pressed while the start sync is still running.
- **Another page's copy written over:** if the stored record of the hero a page plays turns out to be one that page neither read nor wrote, another page wrote it meanwhile. That happens when another tab took a cloud copy, or when the start sync took one while this page was still loading the hero. The page's next save writes its own copy over it, but first keeps that copy as a backup (`conflict`) and marks the base for that hero lost (`{ lost: <a mark of its own> }`, so that a sync which began with the base already lost still sees a new mark as a change). The next sync then weighs the two copies as a conflict and never takes the page's copy for a mere change. A sync running in another tab at that moment does not put its base back (next rule).
- **A sync and the other pages:** other tabs change the stored heroes and the cloud record while a sync waits on the cloud. A sync reads the record after the heroes, so a deletion recorded before it read them is honoured in that sync. It replaces or drops a hero only while the stored record is still the one it read (a hero restored, played or deleted meanwhile is left to the next sync). At its end it re-reads the record and puts on it only its own changes: a base or tombstone another page changed since the sync began stands (`test-sync` "a tab's base drop", "a hero deleted while a sync is on its way", "a restore made in another tab").
- **Tombstones.** Deleting a hero records a tombstone locally (and the deleted record goes into the backups). The next sync writes the tombstone to the cloud. Another device that has the hero unchanged drops it (keeping a backup), and nothing brings it back. Only a copy played *after* the deletion (`played` later than the tombstone) survives it, on either side. A device keeps its newest 32 tombstones; so does a Supabase player. A tombstone belongs to the account it was recorded under, see *Account switch*. Inside one browser, a page that deleted a hero takes out the hero's old record if another page writes it back, but only while the tombstone stands, and only a record played no later than the deletion. So a backup restored in any tab stays.
- **Backups**, on this device, newest first. A copy identical to one already kept isn't kept twice. There are two kinds:
  - *Routine* (`cloud`: a copy a newer cloud copy replaced). The newest of each hero is kept, up to 6 in all.
  - *The last copy of a hero that lost a conflict, was deleted, or was replaced by a restore* (`conflict`, `deleted`, `restored`). The newest of each hero and reason is kept, up to 12. Routine ones never push these out. An older one of the same hero and reason (a second restore of the same hero, say) takes a routine place and goes only for room, listed as dropped.
  - If storage is too full, routine ones go first. Anything dropped for room is listed in the panel (*No longer kept: …*).
  - Settings › Cloud save lists them. A tap and a second tap restore one; a backup is named by its hero and time, so a sync that adds a backup between the two taps doesn't change which one is restored, and the list redraws when it changes. The hero's current copy goes into the backups first, and the restored copy gets `played = now`, or just after the hero's tombstone where that is later (a tombstone dated after a record from a device whose clock was ahead, or made on such a device), so that the restore outlives the deletion. It goes up at the next sync, unless another device changed the hero meanwhile; then the conflict rule applies.
- **A newer version's hero is not taken.** A cloud copy with a class, difficulty, item base, legendary or blessing this version doesn't know, or a level or item level past its caps, is refused (`newer`, "reload the page"). `repairHero` would strip those, and a sync would then carry the stripped copy to every device. A page also writes every stored hero it isn't playing back byte for byte; only its own in-memory copy is made whole (`repairHero`). So a record a newer tab of the same browser wrote survives an older tab's autosave. Nor does an older page take such a hero up on its own: the title shows it greyed, "reload the page", and `startHero` refuses it (`save.js` `heroBlocked`, `freshHero` returning null). The same test also fits a record no version reads (a damaged or tampered save), so the hero is never locked out: a tap on it, or on Continue when it is the last hero, asks once more ("Load it repaired? … Tap again"), and the second tap takes it up made whole (`freshHero(h, true)`). Before that its record as stored goes into the backups as `repaired`, kept like a lost conflict's, and its base is marked lost by the write that first stores the repaired copy (in the same step, so no sync reads the record and the mark apart), so the next sync weighs the repaired copy against the cloud's as a conflict (the copy further on wins, the other is kept) and never pushes it as a mere change. A hero of a class this version does not have is never offered this (`heroRepairable`): repair mends items, levels and the like, not a class, so it only says "reload the page"; an unknown difficulty becomes the nearest this version has. Co-op offers only a hero this page can play (`coop.mjs cheat`).
- **Old saves sync untouched.** What goes up is the stored JSON text, byte for byte. Supabase stores it as `text`, not `jsonb`, so key order and numbers survive. A v13/v14 hero comes back identical (`test-sync` "old saves", scenario `cloud` `oldField`).
- **Offline or failed calls change nothing locally.** A failed `list` ends the sync before anything happens. A failed `get` leaves that hero as it was. The base only moves after a write succeeds.
- **Two tabs:** one page of the browser syncs at a time (a Web Lock, `skotos-cloud`). A page that finds another one syncing leaves it to that one. A tab playing a hero writes its record every 20 s and on hiding, so a sync in another tab treats it as a local change. If another tab takes another device's copy into storage while a tab plays that hero (a tab left hidden for long, say), the playing tab's next save keeps that copy as a backup before writing its own, and the next sync weighs the two as a conflict (see above). Two pages playing one hero are still last write wins (`docs/HANDOFF.md`).
- **When:** at start (the title); then only when something stored has changed (at most every 120 s while a hero is being played, every 20 s on leaving a zone). Other devices are checked every 10 minutes, and when the page comes back into view after a minute away. Settings has *Sync now*. When the page is hidden or closed, the hero being played goes up on its own (best effort, no list first). It's refused `conflict` if the cloud changed in the meantime, and the next sync handles it.
- **A view that may not write** (a write refused `read_only`): for the rest of the visit no change of its own starts a sync, and none is tried on hiding. Only pull-only syncs run (the list, then the copies taken), when the page comes back into view and every 10 minutes.
- **Account switch:** a base belongs to one account (`art:<uid>`, `sb:<player>`). A different account (a code taken, a different claude.ai user) starts with no base, so both sides merge and nothing is lost. Tombstones belong to an account too. The other account's are kept aside for it (`away`, up to 4 accounts) and apply again only when it is back, so a deletion made under one account never deletes a hero from another account's cloud or devices. Deletions made before the browser had any account go to the first one it syncs with.
- **Limits, client side:** 96 KiB per hero (a real one is about 20 KB) and 12 heroes in the cloud. Past those, the extra heroes stay local only and Settings says why.

## claude.ai (the artifact)

There's one document per hero: `data/users/<uid>/h-<hero id>`, with body `{ k: 'hero', id, rev, played, sum, del, at, data, chain }`, where `data` is the hero's JSON text and `chain` the sums of its last 128 revs (`{ rev: sum }`). A write takes a short lease of the document (`acquire`, a holder of the page's own, 10 s), reads it, checks that `rev` is the one expected, writes `rev + 1`, then shortens the lease to the least there is (1 s; the db has no release). A page that finds the lease held is refused `conflict`, and the next sync tries again. Leases only bind callers that use them and a lease can lapse under a slow call; a runtime without `acquire` writes without one. Then two devices can still both write the same `rev + 1`, and the later write stands. The device whose write did not stand finds the cloud's chain naming another hero at the rev it agreed on, and weighs the hero as changed on both sides (the copy further on wins, the other is kept as a `conflict` backup). It does not take its own rev for an unchanged cloud. Every write also names the sum it agreed on at the rev it expects, and is refused `conflict` when the document holds another hero at that rev, so not even the page-hide push (`pushOne`) of the device whose write did not stand goes over the one that stood. A base rev ahead of the document's is weighed the same way. A base rev the chain no longer reaches (a device away for more than 128 writes, days of play) proves nothing: a copy unchanged since takes the cloud's as a routine one, so that backups kept for real conflicts are never pushed out by ones that were none.

If `claude.use('db')` or `claude.use('user')` resolves `null`, or `id()` is null, cloud save is off and the game behaves as before. Settings then says to sign in to claude.ai. That covers being signed out, an older viewer, and a page served outside claude.ai.

**Who can save** (`db.d.ts`, contract 0.2.91): writing, the viewer's own `data/users/` subtree included, needs `interact` or above. That is:

- the artifact's owner;
- on a plan with other members (Team, Enterprise), the members of the organization who can open the artifact at Contributor or above, and a member who arrives by a public link (that link gives them `interact`);
- an Editor from outside the organization, invited by email, **only while the artifact is not also shared by a public link**.

Everyone else holds `view`: Viewers and Commenters, and **every signed-in visitor from outside the organization**, whether invited by email (as Contributor or Viewer) or arriving by the public link. They read their own documents but cannot write them. Their first write is refused `invalid_argument`, the game shows "view-only access cannot save to your account", and their heroes stay in their browser as before (pull-only syncs still take what their own documents hold). So on a personal plan, an artifact shared by a public link (as co-op needs) saves to the cloud for its owner only; friends play with their heroes in their own browsers. A signed-out visitor has no db at all.

### The capabilities to publish (the lead)

A non-empty object replaces the full set, so it has to restate room and user:

```js
capabilities: {
  room: { topics: { s: 'interact', w: 'interact', i: 'interact', f: 'interact', c: 'interact' } },
  user: { scopes: ['profile'] },
  db: {}
}
```

`db: {}` keeps the defaults: shared documents read at `view` and written at `interact`, and each viewer's `data/users/<id>/` subtree private, readable by its own viewer at `view` (so a view-level player's pull-only sync still finds their saves) and written at `interact`. Do not lock the root (`{ path: '', write: 'owner' }`): `can('data.write')` then answers false for every Contributor, and co-op's send advice (`net/coop.js`) hides the co-op button for exactly the friends the owner invites. Nor would it protect the db's caps: every Contributor can still create documents under their own subtree, and those count toward the same 25,000 documents and size. The game itself bounds what it writes (one document a hero, at most 12 live heroes and 32 tombstones a viewer).

After publishing, check once with `ArtifactData` `list` on `data/users` at a Viewer's `as_level`: it should show nothing (another viewer's subtree reads as missing).

## The web build (Supabase)

### Identity and the save code

- The browser signs in anonymously **once** and keeps the session in **localStorage** under `skotos-save-auth`, with a client of its own. Co-op's session is per tab, in sessionStorage (`skotos-auth`), so two tabs are still two co-op players while both save as one browser. The save user is marked `app: 'skotos-save'`. The co-op cleanup query in `docs/coop/supabase.md` (`app = 'skotos'`) doesn't touch these users.
- A visitor who never plays makes no user: the build signs in only once there's a hero stored, or when a code is typed.
- The server links each user to a **player**, and the saves belong to the player. `save_hello()` creates a player for a new user, along with a **code**: 80 random bits (from `gen_random_uuid`) written as sixteen characters of Crockford base 32 and shown as `XXXX-XXXX-XXXX-XXXX`. The server stores only `sha256('skotos-save:' || code)`, so the code is shown once and the page keeps it in localStorage (`skotos.cloud.code`, as `{ player, code }`) to show again.
- **The page names the player.** Every call of the player's saves (`save_list`, `save_get`, `save_put`, `save_delete`, `save_new_code`) passes `p_player`, the player the page believes it is on, and the server refuses `{ error: 'moved', player }` when it has the user on another one. That happens when another tab of the browser took a code (the session is shared through localStorage), when a claim went through but its answer was lost, or when a New code on another device let this user go. The backend then asks `save_hello` again and takes the server's player, and the sync ends before it changes anything; the next one starts from that player's base and tombstones. So one player's base or tombstones are never applied to another player's heroes (`test-saves` "the server moved the user"). *Restore from a code* holds the `skotos-cloud` lock around the claim and the sync after it.
- **The code shown is checked.** `save_hello(p_code)` answers `code_ok` for the code the page keeps, compared with the caller's own player only. The page shows a code only once the server has said it is the player's: made, claimed or renewed with its answer here, or `code_ok`. A kept code that is not (a New code made on another device, a claim or New code whose answer was lost) is dropped, and Settings says there is no code here and offers *New code*. A claim whose answer was lost asks `save_hello` with the claimed code, and counts as done when the server says it is now the player's code.
- **Moving to another device:** Settings › Cloud save › *Restore from a code*. Typing is forgiving: lower case, dashes and spaces are fine, and O/I/L are read as 0/1/1. The new device's user is linked to that player and syncs both ways. A device with no hero claims the player directly, without creating one of its own. If the device already had a player that nobody else uses, its heroes move to the code's player (unless the code's player already has that hero id), and the old player is deleted.
- **A lost session with the code still kept** (site data partly cleared, or the anonymous user removed from the project): the page signs in again and claims its kept code by itself. The kept code is replaced only by a code the server answered for. If the claim ends without a clear answer (offline, its answer lost, the tries spent), the code stays as it is, marked (`skotos.cloud.claim`), and the cloud stays off until a later start settles it. The one exception is when `save_hello` then shows the user tied to another player, which means the claim went through. If the server says the kept code is no more (`bad_code`), the player's own new code is kept instead. With the project's players cap reached, `save_hello` makes no player for an untied user and answers `{ player: null, quota: true }`, and the page still claims its kept code (a claim makes no player), so a browser whose first claim failed is not locked out of its own player.
- **New code:** the old code stops working, and **every other user tied to the player is let go**: whoever took the code from where it was seen loses the heroes with it, and the player's own other devices must type the new code again (until then each saves under a player of its own; nothing local is lost, and the claim merges them). Settings says so before the second tap. Any tied user may make a new code, so a code seen by someone else should be renewed at once.
- Guessing a code: 5 tries per user at once, then one every 2 minutes, and Supabase allows 30 new anonymous users per hour per IP. Against 2^80 codes that's hopeless.

### Bounds (so no visitor can fill the 500 MB free database)

| what | bound |
|---|---|
| one hero | 96 KiB of JSON text (`too_big`) |
| heroes per player | 12 live (`too_many`) and the newest 32 tombstones |
| writes per user (put, delete, new code) | 20 at once, then one every 5 s (12 a minute) (`rate_limited`); the bucket is the user's, so no user tied to a player can spend another's |
| code tries per user | 5 at once, then one every 2 minutes |
| the project's saves | `skotos.save_quota.bytes_cap`, 64 MiB as created (each row counted as its data plus 200 bytes) (`quota`); past it a hero already kept may still grow into `reserve`, 16 MiB, and only new heroes are refused, so visitors who fill the project never stop the players already there from saving |
| the project's players | `players_cap`, 20,000 (`quota`) |

A hero is about 20 KB, so 64 MiB holds about 3,000 one-hero players or 270 players with 12 heroes each. Text over 2 KB is TOAST-compressed on disk, so the real footprint is smaller. Co-op's own cap keeps `realtime.messages` under about 250 MB. Together with Supabase's own ~50 MB, the free plan's 500 MB holds. To change the caps: `update skotos.save_quota set bytes_cap = ..., reserve = ..., players_cap = ...;` (running the migration again keeps them). Check with `select bytes, bytes_cap, reserve, players, players_cap from skotos.save_quota;`. Anonymous sign-ins cost a griefer nothing but Supabase's own limit per IP, so a determined one can still fill `players_cap` (new visitors then get no cloud save) or the bytes up to the cap (new heroes refused): turning on CAPTCHA for sign-ins (Authentication › Attack Protection) is the owner's stronger lever.

Security: every table has RLS on with no policy and no grants. Every page function is `SECURITY DEFINER` with `search_path = ''`, executable by `authenticated` only (never `anon`), and finds the caller's player from `auth.uid()`. Another player's hero reads as missing. The helpers (`save_make_code`, `save_hash`, `save_player`, `save_spend`, `save_norm_code`) aren't executable by pages.

### What the owner or lead must run

1. **Apply the migration** `supabase/migrations/20261027120000_skotos_saves.sql`: paste it into the SQL Editor of project **skotos** (ref `twabjiurbqhqmxzcokqj`) and run it, or use `npx supabase db push`. Running it again changes nothing, and running it over an earlier version of it brings that to this one (the old functions of other arguments dropped, the write buckets moved to the users). It touches nothing of co-op's. The schema `skotos` is already exposed and anonymous sign-ins are already on (co-op).
2. Rebuild and deploy the web build (`npm run build:web`, via the Pages workflow as before). Nothing new in the environment.
3. Then the live check: open the site and play a hero for a moment. Settings › Cloud save should say *On*, with a code. In a private window, type the code and the hero should appear. In the SQL Editor: `select count(*) from skotos.saves; select * from skotos.save_quota;`.
4. Optional, after a while: the Security Advisor lists the seven `save_*` functions as definer functions callable by signed-in users. That's intended, the same as co-op's four.

Each sync lists the player's heroes. On Supabase `save_list` sends no data. On the artifact, a collection `get` returns whole documents (about 20 KB a hero), so a sync with 12 heroes downloads about 240 KB; a small heads document was not built.

Clearing old players (not built; for the owner if the database ever grows): `delete from skotos.save_players where used_at < now() - interval '1 year';` (cascades to the saves; then fix `save_quota` with `update skotos.save_quota set bytes = (select coalesce(sum(bytes),0) from skotos.saves), players = (select count(*) from skotos.save_players);`).
